## Polling and parsing

`jpsRain: SourceAdapter<unknown>` has `kind: 'jps_rain'`, `cadence: 300`, `freshness: 'observed'`, `batch: 'per_source'`, no `apiFamily`, and licence `{id: null, label: 'No published terms found (5 Nov 2026)'}`. `fetch` requires one source, validates a positive safe-integer `meta.jps_id`, and calls exactly one `ctx.http` GET to the fixed origin/path `https://infobanjirjpskl.water.gov.my/Rainfall/GetRainfallGraph/{id}` with `Accept: application/json`. Source metadata cannot replace the origin, add query parameters or cause a redirect. Source120 supplies the configured User-Agent, timeout, status capture and no retry. No data.gov.my family budget is consumed. `backfill(source, ctx)` delegates to the same fetch; it retrieves the full published seven-day window.

The pure `parseJpsRainfall(raw: unknown, source: Source): ReadingInput<'jps_rain'>[]` validates the object, exact `stationId === source.externalId`, `data` array and every row before returning. Each finite numeric `rf` becomes `metric: 'rain_5m_mm'`, `unit: 'mm'`, `valueJson: null`, the bound UUID `source.id` and UTC `observedAt`; do not store `dailyrf`. Match the existing `SOURCE_METRICS.jps_rain.rain_5m_mm` contract, already implemented by Source120; no schema migration is needed.

Port the pilot's strict timestamp logic without importing `pilot/`: accept `YYYY-MM-DDTHH:mm:ss` as MYT and its explicit `+08:00` spelling; validate calendar/time fields by round-tripping local components, then emit `Date.toISOString()`. Reject rollover dates, impossible times, other offsets, text/NaN/infinite rain and mismatched stations with `SchemaError`. Exact duplicate timestamp/value pairs collapse; conflicting values at one timestamp reject the whole payload. An empty `data` array remains valid. Do not invent missing rows or enforce complete coverage in this adapter. D12 interprets a value at T as (T−5 minutes, T]; coverage and rolling totals belong to #131.

## Discovery proven by portal requests

The portal does expose a station list, so the issue's static declared-station alternative is unnecessary. Recon in `121-recon/` captured this chain at `2026-11-10T12:15:28.616407+00:00`: `/Rainfall` loads `/Rainfall/Summary`; district 9 loads `/Rainfall/District/9`; that page requests `/Rainfall/LatestData/All`.

The latest-data response contains `table#Online-rainfalldata`, station rows with external station IDs, displayed station names and district text, and `/Rainfall/Station/{internalId}?districtId=0` links. It contains 49 unique internal IDs including `0232901RF` → `75`, `SG. KUYOH DI LRT BUKIT JALIL`, `Seputeh`. Parse those actual table rows; ignore historical/summarised rain cells and map-handler JavaScript. A focused browser-independent markup reader identifies the exact table/tbody, rows and cells, decodes character entities, and reads the fixed relative station path. It never executes HTML or JS and adds no HTML dependency. Validate nonempty names/districts/IDs, positive safe-integer internal IDs and consistent uniqueness of both IDs; malformed/empty/missing table or conflicting rows throws `SchemaError`. Do not silently drop malformed station rows or return a hard-coded catalogue. No request per unbound station is needed. The list does not publish state text: omit `meta.state` rather than inventing it; the genuine graph capture separately publishes state `KL`.

Entries are `{externalId, name, lat: null, lon: null, url: graphUrl, meta: {jps_id, district}}`; stale-after defaults to Source120's `2 * cadence = 600` seconds. Graph capture coordinates are null. Newer list HTML has map coordinates, but #121 explicitly accepts null coordinates; preserve nulls and archive the newer evidence without embedding numeric coordinates in adapter code. Future use of list coordinates is a product/contract decision, not a reason to type constants.

`SourceAdapter.discover()` has no context and Source120 calls it directly before its catalogue transaction. Export `createJpsRainAdapter({discoveryHttp?, userAgent?} = {})` for test transport/config injection and `jpsRain = createJpsRainAdapter()`. Resolve default transport (`globalThis.fetch`) and required `process.env.ADAPTER_USER_AGENT` only when executed `discover()` runs; an explicit nonempty factory User-Agent overrides the environment, and missing/blank configuration fails visibly. Discovery makes one fixed GET with `Accept: text/html`, configured User-Agent, manual redirects, a 20-second abort deadline and no retries. Throw typed HTTP/network/timeout errors; parse shape errors are `SchemaError`. There is no apiFamily or family budget. Environment access stays at this server discovery boundary; pure parser and indicator modules import no process/Node/worker modules. This avoids changing Source120 composition or the discover signature.

Archive the response byte-for-byte as `docs/sources/infobanjirjpskl.water.gov.my/rainfall-latest-data-all-20261110T1215Z.html`, with a capture note documenting the chain and manifest hashes. Test against a byte-identical copy under the sources fixtures. Latest-data body: 228,937 bytes, SHA-256 `2bbe128c892708226c4419a57ce401e57d4933d1feab3e99ed0f5a8254a82d8b`. The original graph fixture is 127,043 bytes, SHA-256 `25cae3be496cff29b9925595d23fc63b7ddf9c1a4fb29e22b806b00d4ed3bd95`.

## Registration and production evidence

Add `jpsRain` to `packages/sources/src/adapters/index.ts`. Add `infra/environments/production/jps-rain.tf` using existing `../../modules/job`, name `adapter-jps-rain`, arguments `["job", "adapter", "jps_rain"]`, schedule `*/5 * * * *`, zone `Asia/Kuala_Lumpur`, `max_retries = 0`, and existing local job identity/env/secrets/dependencies. Existing Source120 `sourcePart().jobs.adapter` already routes this command; no new worker part is needed.

Inherited first-bind admission discrepancy in the inspected baseline: `jobs.runAdapter` runs backfill, then includes the same source in the normal poll when backfill returns `complete`; newly executed `runBackfillOnce` does return `complete`. Thus its first invocation can issue two GETs for one gauge. Recheck the merged Source120 successor before execution; #121 must not claim its one-request-per-gauge-per-slot budget while that path remains. Controller resolution after Source120 merge: this task may make only the narrow private per-source backfill/result handoff needed to let a fresh backfill satisfy the immediate first polling pass, preserving its backfill purpose and normal polling at the next cadence. Cover job-first/event-first reuse without process caches, fabricated slots, skipped real backfill or public context changes. Initial live freshness may remain unavailable until the first normal poll; do not recast a backfill as one. Backfill plus subsequent normal poll should be tested as separate request purposes, not hidden behind a single aggregate count.

Known inherited telemetry gap: the existing Scheduler → Cloud Run Admin `:run` module cannot forward the actual scheduled instant to `--scheduled-at`. This job therefore records `scheduled_at: null` and lag null. Never derive an invented slot from wall-clock execution time. This does not block rain ingestion; resolving scheduler lag belongs to the shared scheduling seam and must remain explicitly unclaimed.

After implementation and authorized production apply/deploy, capture two manual executions and their persisted polls, waiting for the 15-minute ingest batch: first roughly 2,000 rows, second 0–2 according to actual upstream changes. Then measure a complete 24-hour schedule (288 slots per bound gauge), actual poll count, errors and median `received_at − observed_at` for newest readings per successful poll; do not include all seven-day backfill observations in this freshness median. Report actual data and any missing/duplicate slots. These observations cannot be manufactured or replaced by local fixtures; the 24-hour criterion remains open until elapsed real production evidence exists. Honour the existing deployment freeze and do not use P0 resources.
